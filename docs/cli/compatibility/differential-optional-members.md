# Optional-member executable differential

This supplements the minimal/common operation matrix with **42 actual AWS CLI
observations across 25 representative operations**. It exercises explicit
optional structures, repeated lists, metadata maps, headers, queries, timestamps,
XML attributes, binary payloads, and omitted versus empty values. It does not
claim coverage of every optional member, every model row, or every combination.

- Acceptance: `test/ex_storage_service_cli/executable_optional_member_matrix_test.exs`.

Paths above are relative to `apps/ex_storage_service_cli`. The fixture also pins
the locked S3 model digest. Capture refuses an executable with a different
digest, uses literal loopback IP endpoints, clears provider and proxy environment
variables, disables metadata credentials and pagination, limits retries to one,
uses fixture credentials and temporary files, and shuts every peer down in
`finally`. No live cloud resources are used.

Inputs and response XML are explicitly authored. The AWS executable supplies
the expected requests, output, errors, and downloaded bytes. Expected wire
requests are never generated by ESS. Each observation retains the complete
response status, headers and bytes; request method, path/query, stable headers
and bytes; stdout, stderr, exit status; and downloaded file bytes when present.

## Assertions and metadata

The executable matrix compares exit status, stderr, complete decoded JSON
output, downloaded bytes, method/path/query, stable headers, and XML semantics
or exact binary bytes. XML sibling order and empty-tag spelling may differ;
checksums are recomputed against each executable's actual body independently.
Test-local CRC64NVME and CRC32C implementations are checked against the published
`123456789` vectors; production checksum code is not used for expected digests.
Checksum mode/type control headers are compared as ordinary header values.

Separate raw-client calls verify successful response status, request ID and all
supplied headers, plus service error category, code, HTTP status, operation,
request ID, bucket region and service message. The fixture retains the supplied
host ID; this report does not claim that the CLI exposes that header as an
additional structured error field.

## Invalid provider checksum boundary

For nine uploaded bytes `fixture\x00\xff`, the SHA256 is
`g3+lepvvra2cwHTwimUqhSh7/MAV+81hrTegVPmJQw8=`. A deliberately inconsistent
provider response returns `YWJj`. The pinned AWS executable accepts that response
and prints its checksum. ESS deliberately rejects it with
`:upload_checksum_mismatch` and CLI status 255, preserving upload integrity.
The captured AWS request/output remains unchanged for this divergence.

This test found a real client error-handling bug: unequal-length digest strings
reached `:crypto.hash_equals/2`, which raises `ArgumentError` rather than returning
false. `UploadChecksum.equal?/2` now checks lengths before constant-time
comparison, so malformed provider digests return the existing typed mismatch.
A reproducing unit test covers short, long, empty, malformed and nil returned
digests across all retained checksum vectors. The valid service digest still
passes the same end-to-end matrix; no production integrity check is weakened.
